一份工程笔记。记录一个具体的痛点、我们做的四层措施、以及每一层是被什么样的失败逼出来的。

背景: 一个大型 C++ 平台仓库，功能迁移类工作，代码由 AI agent 主要撰写，人做审查和发布。

---

## 症状

一个循环，重复到让人怀疑流程本身:

```
提交 draft revision -> 收到 comments -> 修 -> 再提一版 -> 收到 comments -> 修 -> ...
```

主观感受是"每个 CR 都要来回很多次"。但主观感受不能拿来改进流程，所以第一步是把它变成数字。

## 第一次测量: 我们数错了东西

先看最顺手的指标，**发布出去的 revision 数**。最近三个 CR 分别是 3、1、1 版。

看起来完全正常。

问题在于 revision 不是成本单位。一个 draft revision 背后可能是十几次本地 `git commit --amend`，每一次都对应一轮"我发现点东西 -> 改 -> 再看"。真正被消耗的是这个。

我们的 commit message 里有一个 agent 署名字段，每次 amend 追加一个分号分隔的条目，所以它天然是个 amend 计数器:

```sh
git log -100 --format='%H %s' | while read -r sha rest; do
  n=$(git show -s --format=%B "$sha" | sed -n 's/^AI-Agent: //p' | awk -F';' '{print NF}')
  [ -n "$n" ] && echo "$n $sha $rest"
done | sort -rn
```

结果:

| commit | amend 次数 |
|---|---|
| 提交 A | 23 |
| 提交 B | 9 |
| 提交 C | 7 |
| **我们的平均** | **13.0** |
| 同仓库其余 74 个 commit | 均值 3.08，中位数 2，众数 1 |

**4.2 倍。** 而发布出去的 3/1/1 把这件事藏得严严实实。

第一条教训: **数 amend，不数 revision。** 你看得见的那个指标，往往是被优化过的那个。

## 根因: 是顺序，不是模型

拿到 13.0 这个数字后，很容易得出"模型不够强"的结论。但把那些 comment 逐条归类之后，事情不是这样。

真正的成因是**工作顺序**:

1. 改动被 push 出去
2. **然后**才发生 review — 我自己的、同事的、或者机器人的
3. 每条 finding 各自一次修复、一次 amend、一次 revision
4. 回到第 2 步

这个循环里没有任何一步是错的。错的是它们的顺序。所有这些 review 里，**绝大部分本来都可以在第一次 push 之前跑完**。把它们放在 push 之后，等于主动把一次批处理拆成十几次串行往返。

还有一个隐藏成本让循环更贵: 在我们的评审系统里，往一个 draft revision 上 push 会 upsert 并**删掉该 revision 上的所有 comment**。所以每一轮不只是浪费一次 push，还会销毁上一轮的审计痕迹。有一次一整轮 reviewer 的意见就这么消失了，只能从会话记录里捞回来。

## 措施一: 把所有 review 提到首次 push 之前

规则本身很短: **凡是能在首次 push 前跑的 review，全部在 push 前跑，一个 batch，改一遍，amend 一次。**

对应一个脚本 (`cr-selfreview`)，并行跑三个 reviewer，输出一份报告:

| reviewer | 它抓到别人抓不到的东西 |
|---|---|
| 机械门 | 引用、计数、语法、描述预算、缺失的证据块、review 过程泄漏。零判断，所以不该占任何人的 review 预算 |
| 另一个 harness 上的 agent | 换一个模型读工作树，先加载审查清单再读 diff |
| 服务端那条 analyzer/critic 流水线 | 就是 push 之后会自动跑的那一条，提前到 push 之前跑 |

第三个是关键。那一轮以前是要用**一次 revision** 去换的，现在不用了。

配套一条原则，比脚本本身更重要:

> **机器人的输出是输入，不是覆盖率。**

一次 Pass 的证据权重是零。我们回溯过六个已合并的 CR，里面约 26 个实质缺陷，**自动化审查找到 0 个**，其中两个 CR 还拿到了明确的 "no critical issues detected" — 而它们各自压着一个真缺陷。所以两个 agent 即使返回 APPROVED，报告里也一律标成 WARN，并且**永不参与决定退出码**。它们的每条 finding 都是待证假设。

## 措施二: 指令挡不住，所以做成阻断门

写完规则以后，规则被跳过了。

这不是态度问题，是结构问题: 一条"你应该先跑自审"的指令，和一个"没跑自审就不许 push"的门，是两种东西。前者在赶时间的时候一定会输。

所以加了一个 `PreToolUse` 钩子，挂在"创建 CR revision"这个动作上，三个条件全满足才放行:

1. 存在一份对应当前 HEAD 短 SHA 的自审报告
2. 报告比 commit 更新 (审完之后又 amend 过，报告即失效)
3. 报告里没有 FAIL

解析不出 git 仓库时直接放行，所以它不会挡到无关的操作。

逃生口只有一个文件:

```sh
touch ~/.cr-push-override
```

钩子消费它然后删除，所以只覆盖一次 push。**关键设计: 这个文件只能由人来建，agent 不许自己建。** 一个 agent 能自己写的 override 不叫门。

这一层的存在理由，就是上一层没能单靠自己站住。

## 转折: 缺陷面移动了

措施一和二起效之后，出现了一个我没预料到的现象。

某个 40 行、单文件的重构 CR:

- 12 项机械门全过
- 引用检查 14 处引用，0 FAIL
- 两个 agent 各自返回 0 issues
- 前后 3 次 amend，代码缺陷 **0 个**

然后收到 4 条 comment。**全部在描述里，没有一条在代码里。**

这和一个早先的测量吻合: 我们收到的 comment 里，大约**一半是关于描述里某句话写错了、说过头了、或者已经过期**，不是关于代码的。这一次是 100%。

结论: **代码的缺陷面收敛了，缺陷面搬到散文上去了。** 而我们的审查火力当时几乎全部对着代码 — 九大项审查清单管代码，描述只管格式和长度。

## 措施三: 给描述也上门禁

那一轮里最贵的一条 comment，指向 `**Solution**` 里这句话:

> The payload bytes cannot move. The helper writes the four keys in the order both call
> sites used, and the values keep their size_t type.

两个理由都不成立:

- **"按原来的顺序写"无关。** `nlohmann::json` 的 object 底层是 `std::map`，`dump()` 输出时按 key 名排序，插入顺序根本到不了字节层面。
- **"值保持 size_t 类型"答非所问。** 类型从来没变过，变的是**表达式**。

真正成立的理由 — 两个被替换的表达式在两个调用点上本来就相等，而且这件事在同一个文件里可以逐行证明 — **一个字都没写**。

### 一个盲区: 引用检查器只能给"存在的引用"打分

为什么 14 处引用 0 FAIL 的检查器没看见这句话?

因为**这句话一个引用都没有**。

引用检查器做的事是: 每个 `file:line` 能不能解析、行是否存在、是否落在空行、句内的 backtick token 是否匹配。它给**已经存在的**引用打分。它没有任何机制去处理引用的**缺席**。

于是形成一个非常糟糕的激励: **最省事写的句子，和最贵的错误，是同一句。** 一句无引用的"这样是安全的"，写它花一行，reviewer 核验它要一次跳出 diff 的阅读，而它错了要花一次 amend。

新增的门 (`Solution claims cited`) 就是补这个: 扫 `**Solution**` 里断言安全性或不变性的句子 — cannot / never / unchanged / identical / equal / preserves / guarantees / enforces / no behaviour change — **本句或下一句之内必须出现 `file:line`**，否则报 WARN。

窗口取两句，因为人的写法就是"先断言，后给证据"。

配套的规则里，更重要的是后半句:

> **引用不了，就删掉。**

一句无引用的断言没有任何上行空间。上面那段话存在的唯一目的是让人放心。**直接删掉比写它好，也比修它好。**

选 WARN 而不是 FAIL 是有意的: 存在合法的无引用断言 — 关于本次新增代码自身的断言，diff 本身就是证据。门要留一点余地，否则会被整体忽略，而一个被忽略的门等于没有。

顺带修了一个自伤: 我那次改完描述，行数从 80 涨到 93，超预算，门报 WARN，**裁剪本身又花了一次 amend**。一轮内容改动付了两次 amend。原因是自审脚本需要一个 commit 才能跑，所以它是在"修它要多付一次"的时刻才告诉你。补的办法很土但有效 — amend 之前先量一下文件:

```sh
sed -n '2,/^=== AGENT_METRICS ===$/p' /tmp/cmsg.txt | grep -c ''
```

## 措施四: agent 的自审结论也是待证假设

这一条是四层里最让我警惕的。

那 4 条 comment 是 AI 辅助的自审产出的。逐条核验之后:

| comment | 站得住吗 |
|---|---|
| `**Solution**` 的论证不成立 | 站得住，而且是这一轮真正的 finding |
| 描述该点名残留的几份 fixture 副本 | 实质站得住，**行号是错的** |
| 同一个问题在第二个位置 | 站得住，与第一条同一个 finding |
| "另一个 CR 在硬件上跑过这个 runner，587 PASS / 1 SKIP / 0 FAIL" | **不成立。整条是编的。** |

最后一条编造了一次测试运行、编造了它的数字、还编造了一段用来佐证的轶事。而被引用的那个 CR 在自己的描述里写的正好相反 — 它明确写着那个 runner 是交叉编译的 ARM 二进制，在构建主机上根本执行不了。它给出的设备数字是另一个 shell 套件的，`587` 这个数在整个 CR 里不存在。

四条里两条带着错行号。

行号错的机制很好理解: 我是**凭记忆**写的，没有回去重读。记忆里的行号会漂到旁边一个长得像的行上 — 那个错引用指向的是 `size_t total = 0;`，而论证需要的是几行之后的 `total = ads.size();`。

编造那一条没有这种温和的解释。

于是三条规则:

1. **引用之前，重新打开那一行。** 不是"我这个 session 读过那个文件"，是现在重读。自审的 draft comment 也要过引用检查器，不能只过 commit message。
2. **绝不凭记忆描述另一个 CR、ticket 或测试运行。引用原文。** 从它的描述里把那句话贴出来。**贴不出来，就丢掉这条 finding** — 不是弱化，是丢掉。
3. **计数、PASS 总数、设备结果，要么从产物里引用，要么不写。** 绝不重建一个。"dry run 过了"在没有日志的情况下不是测试通过的证据；说你手上实际有的东西，通常就是"它编译过了"。

让这件事值得写成规则的，是它的**不对称性**: 一条你丢掉的自审 finding 成本为零；一条错的自审 finding 要花一次 amend，或者被发布出去、拿伪造的数据去引用同事的工作。

这一条对任何用 agent 做审查的人都适用: **你已经知道要怀疑机器人的输出了，但当那个"机器人"是你自己这一侧的 agent、并且它的结论看起来很专业时，怀疑机制会自动关掉。**

## 又一次: 仪表在骗我

上面那个 CR 我当时向自己汇报的是"3 次 amend，接近 3.08 的仓库基线，达标"。

真实数字是 **7**。

原因: commit-msg 钩子对**纯 message amend** 不要求追加署名条目 — 这个设计是对的，纯改文字没有产生代码工作量，记进去会污染统计。副作用是那个字段**完全看不见这类 amend**。

而描述缺陷的修复，**全部**是纯 message amend。

也就是说: 我们的仪表恰好对这个流程当时唯一还在失败的缺陷类是瞎的。7 次是基线的 2.3 倍，不是达标。

顺推一个更难受的结论: 前面那张 23 / 9 / 7 的表，**是下限，不是计数。**

修法是换仪表 — 在飞的 branch 上直接数:

```sh
git reflog show <branch> | grep -c 'commit (amend)'
```

以及一条行为规则: **把纯 message amend 当成真 amend 来做决策。** 它要付一次 push，而 draft push 会删掉那个 revision 上的所有 comment。改文字很便宜，这个便宜感造成了那个 CR 七次 amend 里的四次。

配套还有一条: **纯排版问题不单独 amend**，攒着，等下一次有实质改动时一起带上。判据不是"diff 有多大"，而是"一个相信这句话的读者会不会得到错的结论"。错的 `file:line`、错的计数、代码不支持的断言，都不算排版问题 — 那是永久历史里的假陈述，必须修。

## 现在的结果

诚实版本:

- 最差的那个 CR 从 **23 次 amend** 降到最近一个的 **7 次**
- 仓库基线是 **3.08**，所以**还没达标**，目标是 2
- 代码缺陷已经基本收敛。最近一个 CR 的机械门、两个 agent、三轮 amend，代码 finding 是 0
- 剩下的 comment 几乎全部落在描述上，而针对描述的门是最近才补的，还没有跨多个 CR 的数据

不夸张地讲，最大的收益不是次数下降，而是**知道了成本花在哪里**。之前的判断是"模型不够强"，实际是"顺序错了 + 仪表在骗人 + 缺陷面搬家了没跟上"。

还有一个纯运维教训: 规则得**送得到**。我们的规则文件活在三个位置 (给两个不同 agent 各一份，加一个版本库)。有一天量了一次: 13 个规则文件里，8 个在第二个 agent 那边**完全不存在**，4 个是过期版本，**0 个匹配**。也就是说那之前，那一侧的每个 session 都是在没有任何规则的情况下跑的。现在靠两个同步脚本对齐，方向相反、各自明确谁是源。

## 可迁移的结论

不依赖具体工具栈的部分:

1. **先量，而且怀疑第一个顺手的指标。** 看得见的那个 (revision) 是被优化过的；花成本的那个 (amend) 得自己去挖。
2. **churn 通常是顺序问题，不是能力问题。** 把所有能提前的验证提前，批处理，一次改完。
3. **规则挡不住的地方要上阻断门，而门的 override 不能由被约束的一方来写。**
4. **检查器只能给"存在的东西"打分。** 引用检查器看不见无引用的断言；类型检查器看不见没写的类型。想清楚你的门在哪一侧是瞎的。
5. **修好一个缺陷面，缺陷面会搬家。** 代码干净之后，散文成了新的缺陷面。要跟着搬门。
6. **对自己这一侧 agent 的产出，要用和对外部机器人一样的证据标准。** 它看起来更可信，所以更危险。引用不出原文的结论，丢掉。
7. **引用不了就删掉。** 一句无引用的"这样是安全的"，成本全是负的。
8. **你的度量仪表是系统的一部分，它也会坏，而且往往正好瞎在你当前失败的那一类上。**

最后一条我觉得最值钱: 一个让你自我感觉良好的指标，比没有指标更危险。
