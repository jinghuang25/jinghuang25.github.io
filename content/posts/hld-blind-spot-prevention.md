> 这是一篇个人学习整理。起点是我自己写的两篇内部文档——一篇讲技术决策中的盲点从哪来，一篇是配套的实操 playbook。后来我把它们固化成了一个可被 AI agent 加载的 skill，并配了一个机械门禁脚本。最有意思的部分在最后：那个脚本在评审中被挑出的每一个缺陷，都正好是这套方法论自己列出的原则的实例。
>
> 全文只保留通用的工程原理与方法。所有产品名、组件名、接口名、人名、团队名、工具名与代码路径均已去除或通用化，规模数字仅作量级示意。

## 一句话

设计文档里的盲点，几乎从不来自"想错了"，而来自**决策所依赖的上下文只读到了一部分**；这类错误单看每句话都成立，只有**离开文档去读权威源码**才会暴露。而当我试图把这条规律写成一个自动化门禁时，那个门禁本身又踩了同一类坑六次——这恰好是最好的证据。

# 第一部分：两篇文档讲了什么

## 一个根因，五条原则

所有盲点都是同一个根因的不同形态：**AI（以及人）只拥有其决策所需上下文的一部分**。五条原则覆盖这个差距反复出现的五种形状：

| 原则 | 一句话 | 覆盖的差距 |
|---|---|---|
| **P1 读权威完整源文件** | 读接口的**发送方和接收方**；确认是原始源码而非快照；"不存在"的结论要注明搜索范围 | 读错文件、只读一侧、过期快照 |
| **P2 用代码证据淘汰选项** | 淘汰一个选项前，先找到一个有 `file:line` 支撑的致命约束；"看起来不太可能"不算证据 | 凭假设而非代码评估选项 |
| **P3 不假设已完成或仍活跃** | "已解决"必须说明责任转移到哪；port 遗留路径前先确认它仍有生产流量 | 假性关闭、废弃路径、遗留代码 ≠ 活跃需求 |
| **P4 读实现，不读表面** | 读实现而非名字/调用方；常量从调度配置读；复制先例前验证 backend 是否等价 | API 名称、遗留调用方、错误层级被当作证据 |
| **P5 按影响半径校准验证深度** | 验证投入与"错了有多难修"成正比；由人决定哪些值得深挖 | 平均用力，稀释了高影响项的验证 |

P1–P4 说明**验证什么**，P5 说明**验证多深**。

## 六个案例（已通用化）

**① 只读了接口的一侧。** 早期设计只读了服务端实现，没读消费端脚本。两件事因此不可见：**方向搞反了**（其实是客户端在发命令，服务端需要反向回写），以及一类事件必须由服务端代理转发给客户端——只看服务端那一侧完全看不出来。结果：shim 被设计成单向调度器，实际需要双向代理 + 事件订阅；缺了这条，某个交互流程会在运行时**静默失败**。

**② 从名字估算了接口规模。** 文档写"2-3 个属性"。真读完两侧源码后：一侧 10 种命令，另一侧 6 种回调，还有一整套 JSON 分发 + 回调机制。**4 倍规模误差**传播进了排期、测试覆盖和风险评估——每个下游决策都锚定在一个从未从代码里读出来的数字上。花 15 分钟读源码，能省下三天的方向错误。

**③ 读了构建产物而不是源码。** AI 用的是某个包 build 目录下两年前的依赖快照，而不是主干里的真实源码。这次运气好——协议两年没变；一旦变过，所有接口决策都锚定在一份过期合约上。溯源还牵扯所有权与历史：快照的"最后更新时间"是同步时间，不是源码修改时间。

**④ 隐性阻断因素。** 两个选项被"任何设计文档里都不会出现"的约束淘汰了：一个是**启动时序**（某进程在目标进程启动**之前**就调用了它的接口——这条只写在 init 启动序列配置里）；另一个是**运行时能力**（代码里搜索目标机制得到**零个**引用，那个 runtime 根本没有这个桥接层，后经对方团队确认）。不读这两处，两个选项会在整个设计期都"看起来可行"，只在实现阶段才暴露。
反向也值得做：**先检查目标机制是不是本平台已经有了**——一个看起来"需要新建能力"的选项，可能已经可用，能把一次注定的二次迁移变成"一次到位"。

**⑤ 完成状态的三种假象。**
- **假性关闭**：一个条目被标为"随某框架退役，无需处理"，隐含假设是"那个框架会更早退役"。实际它退役得更晚，依赖在整个窗口期都活着。这次"解决"只是把责任**转移**到了另外三处具体位置，并催生了三个新迁移条目、新负责人和新的评审范围。
- **废弃路径（代价约 500 行）**：因为遗留实现里有三个云消息处理器，就照着实现了一遍。后来确认那类消息只发往另外两个产品线，在当前平台上永远不会触发。连带成为死代码的机制一起删掉，净减约 500 行——**写了、评审了、又删了**。
- **"已合并" ≠ 端到端可用**：某引擎已合入主干，但它的服务端点还是 stub。完成状态是**端到端路径**的属性，不是一次 commit 的属性。

**⑥ 读实现，不读表面。**
- **合约权威在哪**：遗留实现把某个 topic 注册成小写，另一个注册成大写，我们差点照抄这个不一致。真正的权威是分发守护进程的**注册配置文件**，它是大小写敏感匹配的——抄错大小写会得到**静默不派发**（没有报错，只有测才知道）。
- **名字骗人**：一个名字里带 "fast" 的指标上报函数，实现是**同步阻塞的 HTTP POST**。而调用点在一条目标延迟 10ms 以下的 P0 路径上，每次触发都会走到。内联调用会直接堵死这条路径；最后把发送挪进了工作队列。附带一个教训：另一个包内联上报是**对的**，因为它的后端是非阻塞的——**复制先例前要验证 backend 是否等价**。
- **找错层级**：我们假设某个业务 payload 里带着设备序列号或客户 ID，其实两者都没有。身份是在**凭证与签名层**施加的，服务端从已认证的请求里推导出来。在错误的层级找正确的信息，会得到一个**虚假的"不存在"**，进而差点推出错误的架构假设。

## AI 为什么会遗漏——推断出的机制

这部分比案例本身更有迁移价值：

- **搜索满足 + 命名不对称**：找到服务端文件就触发"任务完成"，消费端文件被当作"别人的组件"跳过。它从不会自己推断"我该去找另一侧，哪怕跨语言跨仓库"。
- **模式匹配的虚假置信**：把这个接口和别的小接口类比，在**读任何代码之前**就从名字生成了估算，且没有标注不确定性就进了文档，评审者当成已验证事实。
- **约束位置不匹配**：启动时序约束在 init 配置里，而它的搜索是以组件为中心的，从不延伸到启动序列。
- **能力从 API 名称推断**：名字听起来像通用平台能力，就假设可用。
- **"已解决"被视为终结**：追踪"一次关闭把责任转移到哪"需要跨多轮上下文，而它倾向于把解决当成自包含的。
- **遗留代码 = 活跃需求**：代码存在 → 推断需求活跃，没有信号说明那是平台特定的。

# 第二部分：从文档到 skill

两篇文档写完之后，问题变成：**知识躺在文档里，靠人记得去找、去重新应用。** 于是把它固化成一个可被 AI agent 按需加载的 skill。

## 结构

```
skills/hld-blind-spot-prevention/
├── SKILL.md                       主文档：五条原则 + 流水线 + 主检查清单 + Known Limits + Troubleshooting
├── references/
│   ├── case-studies.md            六个案例（含"AI 为何遗漏"分析）
│   └── prompts-library.md         可复制的 Prompt R/A/B/C/D/E
└── scripts/
    └── assumption-ledger-audit.sh 机械门禁：假设清单里还有未解项就非零退出
```

## 流水线

```
Phase 0  深入而广泛的前期研究          ← 先调研，再动笔
   ↓       广度(枚举全部组件/选项/机制) + 深度(读高影响项的权威源码)
Step 1   假设清单 (Prompt A)          把"我以为"变成显式的 [已确认]/[大概]/[未知]
Step 1.5 选项淘汰 (Prompt E)          先用代码证据淘汰，再对存活项做 trade-off
Step 2   接地 (Prompt B)              双侧接口审计 + 文件溯源清单 + 实现审计清单
Step 3   引用合约 (Prompt C)          每个事实带 file:line，否则标未知
Step 4   对抗性验证 (Prompt D)        必须在全新 session
Step 5   护栏与模型选型               session 隔离 > 模型强度
   ↓
评审前主检查清单
```

## 两个来自他人的关键补强

固化过程中收到两条建议，都改变了结构：

**① "在正式开始 HLD 之前，先做一轮深入而广泛的研究"**（来自一位资深工程师）。这条被做成独立的 **Phase 0**，而不是"预热"——因为它是**假设清单的输入**。盲点的两个方向正好对应研究的两个维度：广度不足 → 隧道视野（盯着第一个找到的组件，漏掉另一侧、别的方案、别的团队、启动序列里的隐性约束）；深度不足 → 表面推断（从名字和类比估算规模与能力）。做法是**先广后深两遍扫描**：第一遍发散枚举、不收敛；第二遍只对高影响项收敛到"读权威源码"。

**② "要完备一些，能 work out 出来一个检查列表"**（来自管理者）。于是有了那份**可直接复制进设计文档或 CR 的主检查清单**，分 A–E 五组：Phase 0 研究与假设清单 / 溯源与实现 / 选项与决策 / 完成状态与活跃路径 / 验证护栏。判据是"缺一项就说明设计还没准备好"。

## 那些"试过但没用"的做法

- ❌ **先写设计，再补假设清单**：假设已经固化在设计里，清单填出来几乎全是"已确认"，毫无价值。**规则：清单必须在第一行设计正文之前存在。**
- ❌ **在同一个 session 里做对抗性验证**：自我审查只能找到格式问题。换新 session 后立刻发现了一个原本被完全忽略的同步端点。**这是护栏，不是建议。**
- ❌ **给验证 prompt 带入结论**："帮我确认接口大概是 X" 会把 AI 带偏。先让它列出能找到的全部，不给方向，再比对预期。
- ❌ **把"未知"当"以后再说"**：它是阻塞项，不是标注出来就算完成。

# 第三部分：最有意思的部分——门禁脚本被自己的原则打了六次脸

那个门禁脚本很简单：扫描假设清单，只要还有"未知"就以非零退出码报"尚未准备好"。**不到 100 行 bash。**

它经过了五轮评审（自动审查机器人 + 一个 AI 评审 agent + 我自己的自查），一共挑出六个缺陷。**每一个都是这套方法论自己列出的原则的实例。**

| # | 缺陷 | 对应原则 | 后果方向 |
|---|---|---|---|
| 1 | 统计**整个文件**里的状态标签 → 文档自带的"状态图例"被计成了活跃项 | P1 没在真实形态上验证 | 假失败（吵闹但安全） |
| 2 | 正则 `\[标签\]` 认不出 `[未知 — 原因]` 形式——**而这个格式是文档自己教读者写的** | P1 没读自己的权威来源 | **假通过**（危险） |
| 3 | 只锚定到"行"没锚定到"单元格" → 叙述性单元格里的提及被误计 | P4 读表面不读结构 | 假失败 |
| 4 | off-ledger 只统计了一种标签，**输出消息却声称三种都报了** | P4 注释/文案是未验证的声明 | 消息说了代码没做的事 |
| 5 | 两条代码路径的大小写与锚定**不一致** → 引用块里的行、小写标签**两边都漏**，静默消失 | 别让"不知道"走到"没问题"的同一条路 | **静默丢失** |
| 6 | （我自查发现）**不可读文件**报告为全零 + "没找到标签"，与干净文档的输出**完全一样** | 同上 | **静默丢失** |

几个值得单独说的点：

**第 2 个缺陷最讽刺。** 文档里明明写着"开放项要写成 `[未知 — 原因]`"，而我给这个格式写的检查器认不出它。这正是 P1 的定义：**没有去读那份权威来源——哪怕权威来源就是我自己写的另一段文字。**

**第 3 个缺陷是靠自测暴露的。** 把门禁指向**这个 skill 自己的 SKILL.md**，它报了 5 个未解项——而那 5 个全是流程图和快查表里的**提及**，一个真实条目都没有。也就是说，文档里"这些行会被排除"的说法，被它所在的那个文件本身**证伪**了。这是那种"在自己的产物上跑一遍"就能发现、不跑就永远发现不了的缺陷。

**第 5、6 个是同一条规则的两个实例**，而这条规则来自我另一个 skill 的开篇：**永远不要让"不知道"和"没问题"走同一条代码路径。** 引用块里的一行、一个小写标签、一个没有读权限的文件——三者的输出都和"干净"一模一样。

**最后一次修法的转变。** 前几轮我都在"补正则"：加个 `-i`、加个锚点。第 5 轮我改了策略——**让 off-ledger 判定成为计数判定的精确补集**（同一段代码里复用同样的条件，大小写靠同一份大写副本，而不是两个独立的开关）。这样"**被门禁拦下的 + 被列出的 = 文件里所有标签**"是**构造上成立**的，不依赖任何人记得两边同步。然后写了个不变量检查，对 3 个文档 + 一个刻意构造的对抗性文件（共 66 个含标签的行）逐行断言：零静默丢失、零重复上报。

**这就是"修实例"和"修类别"的区别。** 前四轮我在修实例，每修一个就冒出下一个；第五轮才修掉了类别。

# 可复用的 takeaway

**关于设计文档**

1. **写之前先做一轮广+深的研究**，产出带引用的研究笔记；它是假设清单的输入，不是热身。
2. **假设清单必须先于设计正文存在**，且定稿前所有"未知"必须归零。
3. **淘汰选项要有代码证据**，"看起来不太可能"不算。隐性约束通常藏在启动序列、runtime 能力、调度配置和跨团队边界里。
4. **"已解决"要说明责任转移到哪**；没有残留记录的关闭就是假性关闭。**"已合并" ≠ 端到端可用。**
5. **名字不是证据**：读实现、从调度配置读常量、复制先例前验证 backend 等价、确认哪个层级拥有你要找的信息。
6. **对抗性验证换一个 session 跑**，这是护栏而非纪律。

**关于给自己的方法论写自动化**

7. **在自己的产物上跑一遍。** 我的门禁指向自己的文档时报了 5 个假失败——这是最便宜、最容易被跳过的一步。
8. **注释、日志和文案都是未验证的声明。** "这里会报告 XXX" 和"代码真的报告了 XXX"是两件事，第 4 个缺陷就是前者说了后者没做。
9. **两条路径判定同一件事时，让其中一条由另一条推导出来。** 平行写两遍正则，就是在等它们哪天不同步——而不同步的后果是静默丢失。
10. **修类别，不要修实例。** 如果补了一个正则之后你说不清"还有哪些形态会漏"，那你修的是实例。
11. **能证明的不变量 > 更多的用例。** 21 个回归用例有价值，但"gated ∪ listed = 全部"这条不变量才真正关掉了这一类缺陷。
12. **写门禁的人最该被门禁检查。** 一个用来防止"未经验证的假设溜过去"的脚本，自己溜过去了六个未经验证的假设。

**最后一条，也是全篇最想留下的**

> **对自己产出的怀疑，要和对别人产出的怀疑一样多**——而且要用**动作**（跑一遍、读另一侧、在自己的文件上自测、证明一条不变量）去表达这种怀疑，而不是用"我再检查一下"。
